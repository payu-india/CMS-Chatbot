# Quick Start: PayU Server-to-Server (S2S)

This guide walks you through the minimal, essential steps to integrate PayU Server-to-Server (S2S) payment gateway, including mandatory request parameters with clear demarcation between generic payment parameters and S2S-specific routing fields, sample requests, and sample responses.

## Prerequisites

Before initiating transactions, ensure you have:
1. **PayU Merchant Credentials**: `key` (Merchant Key) and `SALT` from your [PayU Merchant Dashboard](<redacted URL>).
2. **IP Whitelisting**: Ensure your server firewall allows incoming HTTP/HTTPS traffic from PayU's webhook and callback IP addresses:
   * `180.179.174.1`
   * `180.179.174.2`
3. **PCI-DSS Compliance** (Applicable only if capturing card details directly): SAQ A-EP or SAQ D certification. (UPI S2S integrations do not require PCI-DSS card certification).

---

#### Environment

All S2S transactions are initiated via a server-side `POST` request with `application/x-www-form-urlencoded` encoding.

| Environment        | Base URL                                                                                        |
| :----------------- | :---------------------------------------------------------------------------------------------- |
| **Test / Sandbox** | [https://test.payu.in/\_payment](https://test.payu.in/_payment "https://test.payu.in/_payment") |
| **Production**     | [https://secure.payu.in/\_payment](https://test.payu.in/_payment "https://test.payu.in/_payment") |

## 1. Prepare the Request Parameters & Hashing

To clearly demarcate how an S2S request is constructed, parameters are organized into two distinct categories:
1. **Core Payment Parameters**: Standard transaction details common across PayU integrations.
2. **S2S-Specific Parameters & Routing Fields**: Specialized flags that govern direct server-to-server dispatch, suppress checkout UI redirects, and instruct PayU whether to return an ACS 3DS template, initiate UPI Intent, or trigger a decoupled authorization.

### Category A: Core Payment Parameters

| Parameter | Type | Mandatory? | Description | Example |
| :--- | :--- | :--- | :--- | :--- |
| `key` | String | Yes | Unique merchant key provided by PayU. | `gtKFFx` |
| `txnid` | String | Yes | Unique transaction ID generated by merchant. Max 40 characters. | `TXN_S2S_982341` |
| `amount` | Float / String | Yes | Amount payable in INR with two decimals. | `1500.00` |
| `productinfo` | String | Yes | Product/service description. Max 100 characters. | `Annual Subscription` |
| `firstname` | String | Yes | Customer's first name. | `Priya` |
| `email` | String | Yes | Customer's valid email address. | `priya@example.com` |
| `phone` | String | Yes | Customer's 10-digit mobile number. | `9876543210` |
| `surl` | String | Yes | Success callback URL where PayU posts transaction status on approval. | `<redacted URL>` |
| `furl` | String | Yes | Failure callback URL where PayU posts transaction status on failure/cancel. | `<redacted URL>` |
| `hash` | String | Yes | SHA-512 cryptographic checksum calculated on merchant server. | `4a3b2c...` (128 hex chars) |
| `udf1`–`udf5` | String | No | Custom merchant tracking fields. Non-empty values must be in hash. | `order_ref_123` |

---

### Category B: S2S-Specific Parameters & Routing Fields

These parameters tell PayU's payment engine how to process the transaction directly on the backend without redirecting the customer to PayU-hosted web checkout.

| Parameter | Type | Mandatory? | Description & Allowed Values |
| :--- | :--- | :--- | :--- |
| **`txn_s2s_flow`** | Number | **Yes** | **Primary S2S flow controller.** Governs response packaging:<br>• `1`: **Standard S2S** (Cards Classic, Native OTP, UPI Collect)<br>• `4`: **UPI Intent / UPICC / Decoupled S2S** (Returns JSON with `intent_uri` or 2-step auth payload)<br>• `3`: **Direct Authorization** (Merchant pre-authenticates 3DS externally) |
| **`pg`** | String | **Yes** | Payment category identifier:<br>• `CC`: Credit / Debit Cards<br>• `UPI`: Unified Payments Interface (Intent or Collect)<br>• `UPICC`: RuPay Credit Card on UPI<br>• `NB`: Net Banking |
| **`bankcode`** | String | **Yes** | Specific routing code for the chosen instrument:<br>• Cards: `CC` (Credit Card), `DC` (Debit Card)<br>• UPI: `INTENT` (App Deeplink), `UPI` (Collect via VPA), `UPITEZ` (Omnichannel)<br>• UPICC: `INTCC` |
| **`authentication_flow`** | String | Conditional | Instructs PayU how the customer authenticates:<br>• `REDIRECT`: PayU returns Base64-encoded bank ACS challenge template (`acsTemplate`) for customer OTP entry.<br>• `decoupled`: For 2-step native card decoupled flow. |
| **`auth_only`** | Number | Conditional | Used in Cards Decoupled S2S Flow (`txn_s2s_flow=4`):<br>• `1`: Two-step Auth & Capture (holds funds; captured later via S2S API).<br>• `2`: Authentication-Only (completes 3DS and provides authentication tokens without settlement). |
| **`ccnum`** | String | Conditional | 16-digit card number. *(Mandatory when `pg=CC`)* |
| **`ccexpmon`** | String | Conditional | Card expiry month (`MM`, e.g., `05`). *(Mandatory when `pg=CC`)* |
| **`ccexpyr`** | String | Conditional | Card expiry year (`YYYY`, e.g., `2028`). *(Mandatory when `pg=CC`)* |
| **`ccvv`** | String | Conditional | 3 or 4-digit CVV/CVC security code. *(Mandatory when `pg=CC`)* |
| **`ccname`** | String | Conditional | Cardholder name printed on card. *(Mandatory when `pg=CC`)* |
| **`vpa`** | String | Conditional | Customer's Virtual Payment Address (e.g., `user@oksbi`). *(Mandatory when `pg=UPI` and `bankcode=UPI`)* |

---

PayU verifies transaction integrity using a SHA-512 checksum. Calculate the hash strictly on your server:

### Hash Formula
```
hash = SHA-512(key|txnid|amount|productinfo|firstname|email|udf1|udf2|udf3|udf4|udf5||||||SALT)
```

> **Rules:**
> * Delimit all fields with pipe symbols (`|`).
> * Include exactly 5 empty pipes `|||||` after `udf5` before appending the `SALT`.
> * The output must be in lowercase hexadecimal.

## 2. Post the Request

### Sample 1: Cards Classic S2S Request (with ACS Template)

```bash
curl -X POST `https://test.payu.in/_payment`  \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "key=gtKFFx" \
  -d "txnid=TXN_CARD_1001" \
  -d "amount=1500.00" \
  -d "productinfo=Annual Subscription" \
  -d "firstname=Priya" \
  -d "email=priya@example.com" \
  -d "phone=9876543210" \
  -d "surl=<redacted URL>" \
  -d "furl=<redacted URL>" \
  -d "hash=c5d8869b2d8ff5579979b9a67891234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234" \
  -d "pg=CC" \
  -d "bankcode=CC" \
  -d "ccnum=5123456789012346" \
  -d "ccexpmon=05" \
  -d "ccexpyr=2028" \
  -d "ccvv=123" \
  -d "ccname=Priya Sharma" \
  -d "txn_s2s_flow=1" \
  -d "authentication_flow=REDIRECT"
```

## 3. Handle the Response

### Response 1: Cards S2S with 3DS Challenge (`acsTemplate`)

When a card requires 3D-Secure authentication, PayU returns a JSON response containing an Base64-encoded `acsTemplate` HTML form.

```json
{
  "status": 1,
  "msg": "Redirect to ACS",
  "result": {
    "acsTemplate": "PGh0bWw+PGJvZHkgb25sb2FkPSJkb2N1bWVudC5mb3Jtcy5mb3JtMS5zdWJtaXQoKSI+PGZvcm0gbmFtZT0iZm9ybTEiIG1ldGhvZD0icG9zdCIgYWN0aW9uPSJodHRwczovL2Fjcy5iYW5rLmNvbS9vdHAiPjxpbnB1dCB0eXBlPSJoaWRkZW4iIG5hbWU9IkNyZXEiIHZhbHVlPSJleUpoYkdjaU9pSlN..."
  }
}
```

**Client Processing Instructions:**
1. Base64-decode `result.acsTemplate` to retrieve the HTML form.
2. Render this HTML inside an invisible iframe or webview. The form's `onload="document.forms[0].submit()"` automatically redirects the customer's browser to their bank's OTP page.

---

### Response 2: UPI Intent S2S Response

When initiating a UPI Intent payment (`pg=UPI`, `bankcode=INTENT`, `txn_s2s_flow=4`), PayU immediately responds with the intent URI, application deep links, and QR string.

```json
{
  "status": "SUCCESS",
  "msg": "Transaction Initiated",
  "result": {
    "intent_uri": "upi://pay?pa=payu@icici&pn=MerchantStore&tr=TXN_UPI_2001&am=350.00&cu=INR&mc=5499",
    "deep_links": {
      "gpay": "gpay://upi/pay?pa=payu@icici&pn=MerchantStore&tr=TXN_UPI_2001&am=350.00&cu=INR",
      "phonepe": "phonepe://pay?pa=payu@icici&pn=MerchantStore&tr=TXN_UPI_2001&am=350.00&cu=INR",
      "paytm": "paytmmp://pay?pa=payu@icici&pn=MerchantStore&tr=TXN_UPI_2001&am=350.00&cu=INR"
    },
    "qr_data": "upi://pay?pa=payu@icici&pn=MerchantStore&tr=TXN_UPI_2001&am=350.00&cu=INR"
  }
}
```

---

### Response 3: Final Callback Response (Posted to `surl` / `furl`)

Once the customer completes payment authorization (or cancels), PayU issues an HTTP POST to your configured `surl` or `furl` with transaction details and the reverse hash:

```
status=success
&txnid=TXN_CARD_1001
&amount=1500.00
&productinfo=Annual Subscription
&firstname=Priya
&email=priya@example.com
&phone=9876543210
&mihpayid=403993715530182345
&bank_ref_num=20261106987654
&bankcode=CC
&card_type=MAST
&card_token=tok_cc_98127391
&hash=8f29e10ab645d98e1a...
&error=E000
&error_Message=No Error
```

#### Callback Reverse Hash Verification Formula
Verify the integrity of this callback on your server using reverse order parameters:
```
calculatedHash = SHA-512(SALT|status||||||udf5|udf4|udf3|udf2|udf1|email|firstname|productinfo|amount|txnid|key)
```
